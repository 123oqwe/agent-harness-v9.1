### GLM_API_KEY Environment Variable Leak (CRITICAL DISCOVERY)
- KeyVault constructor calls loadFromEnv() which reads GLM_API_KEY and ZHIPU_API_KEY from process.env
- loadFromEnv() adds env key with created=Date.now() timestamp
- addKey() appends to list; getKey() returns oldest healthy key (sorted by created)
- If GLM_API_KEY is set in env, KeyVault auto-loads it; test's addKey('zhipu','test-key') adds later
- getKey() returns the env key (older created timestamp) instead of test-key
- Tests that pass without GLM_API_KEY FAIL when it is set (mutation runner exports GLM_API_KEY)
- Affected tests (3 failures with GLM_API_KEY set):
  1. tests/gateway/provider-adapters.test.ts: "resolve() returns JSON on success for zhipu" - FIXED (added beforeEach delete GLM_API_KEY/ZHIPU_API_KEY)
  2. tests/gateway/key-vault.test.ts: "supports ZHIPU_API_KEY for zhipu provider" - FIXED (delete GLM_API_KEY before setting ZHIPU_API_KEY, since loadFromEnv checks GLM_API_KEY first)
  3. tests/gateway/managed-gateway-stream.test.ts: "completeStream respects rate limits" - FIXED (beforeEach delete GLM_API_KEY/ZHIPU_API_KEY, was hitting real zhipu API instead of local ollama)
All 3 fixes committed in 1f9c3232. Verified: 603/603 gateway tests pass with GLM_API_KEY set.
- Root cause: tests don't isolate env vars before creating KeyVault instances
- Fix pattern: add beforeEach(() => { delete process.env.GLM_API_KEY; delete process.env.ZHIPU_API_KEY; }) in describe blocks that create KeyVault
- Note: other gateway tests pass because they either don't use zhipu provider or set OPENAI_API_KEY instead
- Also checked: no KeyVault instances in tests/ outside tests/gateway/ (rg verified)
- Also checked: all 6 other KeyVault-creating gateway test files pass with GLM_API_KEY set (107/107)
